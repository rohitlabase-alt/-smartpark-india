## 2026-09-08 — Session 7 (Phase 7 — browser-flake follow-up: reservations "incomplete or malformed" + facility 100)
- **Root cause (bad browser report reproduced & fixed):** a manual browser test against dev surfaced `The reservations response was incomplete or malformed.` (`frontend/src/api/reservations.ts` `fetchReservations`). Cause was NOT new API output: the frontend loads `@smartpark/shared` as the **built** `packages/shared/dist` (runtime `RESERVATION_STATES`), while the dev Vite server at the time was started **directly** (`frontend/node_modules/.bin/vite`), bypassing the root `predev` that rebuilds shared. The DB row `id=5` (PENDING_PAYMENT, created pre-rebuild) is consistent evidence. Also reported: a separate request to `/api/v1/parking/100/availability` — root-caused to a free-text user input in the availability screen (no code path generates it; the dev DB has facilities 1–3). No silent schema/seed changes; `isReservation` unchanged in behaviour, **strengthened** only by also requiring non-optional `amount`/`paymentStatus` per the shared `Reservation` contract.
- **Regression tests:** backend `reservations.integration.test.ts` (+3, DB-backed) — exhaustive 16-field DTO shape (`id reservationCode userId facilityId zoneId slotId startsAt endsAt state amount paymentStatus cancelReason cancelledAt confirmedAt createdAt updatedAt`, membership in runtime `RESERVATION_STATES`/`PAYMENT_STATUSES`) asserted for `POST /api/v1/reservations` and every row of `GET /api/v1/reservations`, plus a full lifecycle test walking create → list → detail → initiate → verify → re-fetch and asserting a complete valid DTO at **every** step. - **Recurrence guard:** `@smartpark/web` gains `predev: npm run build -w @smartpark/shared` so any scripted dev launch of the frontend rebuilds the shared contract first (root `npm run dev` already had this; direct `.bin/vite` now documented as unsupported for post-Phase-7 runtimes).

## 2026-09-06 — Session 7 (Phase 7 — mock payment foundation)
- **Added (backend `modules/` per ARCHITECTURE §3):**
  - Payments (`payments` module) under `/api/v1/payments` (auth required, user-owned): `POST /initiate` (`{ reservationCode }`, optional `Idempotency-Key` header) rechecks the reservation is `PENDING_PAYMENT` (`409 PAYMENT_NOT_PENDING` otherwise, `409 PAYMENT_UNAVAILABLE` when the amount is null) and a non-zero stored `amount`, then creates a `payments` row (provider `MOCK`, deterministic `providerTxnId` `MOCK-<code>-<amount>`, status `PENDING`). With an `Idempotency-Key`, payment creation + idempotency-key claim are atomic (15 min TTL); the same `(user, key, endpoint)` reuses the existing payment instead of creating a duplicate attempt. `POST /:txnId/verify` runs the **entire** verification inside one DB transaction: ownership enforced via a join to `reservations.user_id` (miss → `404 PAYMENT_NOT_FOUND`, no IDOR/enumeration); on provider SUCCESS the payment → `SUCCESS`, reservation → `CONFIRMED` (with `confirmed_at`, `payment_status='SUCCESS'`), and a `CHARGE`/`SUCCESS` ledger transaction is recorded; on provider FAILED the payment → `FAILED` and reservation → `FAILED` (never `CONFIRMED`) with a `CHARGE`/`FAILED` transaction. Re-verifying a SUCCESS payment is idempotent; re-verifying FAILED → `409 PAYMENT_ALREADY_FAILED`; verifying once the reservation is no longer pending → `409 RESERVATION_NOT_CONFIRMABLE` (whole tx rolls back — payment stays `PENDING`, reservation unchanged). `PaymentProvider` interface + deterministic `MockPaymentProvider` (failure iff txn id ends with `__FAIL__`; no secrets/cards/external API); `app.ts` mounts `buildPaymentsRouter()`.
  - Reservation lifecycle rework (`bookings`): `create` now computes `amount` from the facility `pricing` JSONB `hourlyRate` (default ₹100/hr — D-035), inserts `PENDING_PAYMENT` with `payment_status='INITIATED'`; `confirmOnPayment`/`markFailed` implement the payment transitions; customer `cancelBooking` allows `PENDING_PAYMENT` + `CONFIRMED` (no refund — D-035).
