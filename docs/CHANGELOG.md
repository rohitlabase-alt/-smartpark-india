## 2026-09-16 — Session 11 (Phase 9, Block 4.2 — operator force-exit / session cancellation)
- **Backend — operator force-exit (`sessions` module, D-039):** `POST /api/v1/parking-sessions/:id/cancel` → `200 { session }`. **Operator-only**: route `requireRole("PARKING_OPERATOR")` + service `assertVerifiedOperator` (`403 OPERATOR_NOT_VERIFIED`); a reservation owner is rejected (`403 FORBIDDEN`) and must use `exit`. The session is resolved by an operator-ownership SQL join (no `facilityId` is trusted from the body); foreign/unknown/other-facility sessions → `404 SESSION_NOT_FOUND` (no existence disclosure). Body `{ reason?: string }` (≤500, zod `.strict()`).
- **State machine (one transaction):** session `ACTIVE → CANCELLED` (guarded `UPDATE … WHERE status='ACTIVE'`, `exit_at` stamped), slot `OCCUPIED → AVAILABLE` (existing guarded release, operator-set statuses preserved), reservation `ACTIVE → CANCELLED` (`cancel_reason` = trimmed reason/`null`, `cancelled_at` = now), availability cache re-mirrored, `PARKING_SESSION_CANCELLED` audit record (`{ facilityId, slotId, reservationId, cancelledBy: "OPERATOR", reason?, slotReleased }`). No refund (D-035 unchanged). New repository helpers `findSessionForOperator` (FOR UPDATE OF s), `cancelSession` (guarded), `lockReservationForUpdate`; reuses `releaseSlot`/`upsertAvailabilityState`/`reservationsRepository.updateState`.
- **Concurrency:** lock order session → reservation → slot serializes a force-cancel against a concurrent normal exit; the guarded session transition means **exactly one** wins, the loser (or a repeat / already-`COMPLETED`/`CANCELLED`) gets `409 SESSION_NOT_ACTIVE` and the transaction rolls back with state unchanged. The released slot is immediately re-bookable.
- **Shared:** `AUDIT_ACTIONS` +1 (`PARKING_SESSION_CANCELLED`).
- **Frontend — `api/sessions.ts`:** `cancelParkingSession(accessToken, sessionId, reason?)`. `OperatorDashboard.tsx`: per-session "Cancel session" control with an inline confirm + optional reason textarea (`cancel-session-reason-*`), request-id-guarded handlers, error mapping incl. `OPERATOR_NOT_VERIFIED` and stale-`SESSION_NOT_ACTIVE` auto-refresh. `AdminPlatform.tsx`: audit label `PARKING_SESSION_CANCELLED`.

## 2026-09-16 — Session 9 (Phase 9, Block 3 — pass/gate tokens + slot-occupancy control)
- **Backend — parking-pass token (`pass-token.ts`, `sessions` module):** deterministic HS256 JWT signed with jose, prefix `ppk_`, claims `{ scope: "parking:entry", sub: reservationCode }`, **no `iat`** (byte-deterministic), `exp` = reservation `ends_at`. `GET /api/v1/parking-sessions/by-reservation/:code/pass` → `200 { verificationToken }` — owner or the facility's VERIFIED operator only (`404` otherwise, no existence disclosure); `CONFIRMED` only (else `409 RESERVATION_NOT_ENTRYABLE`); repeat reads are byte-identical (a pass is never rotated/turnovered — a re-request can't invalidate an earlier one). Only the SHA-256 digest is persisted (`reservations.verification_token_hash`, lazy in-tx backfill for pre-migration rows).
- **Backend — gate entry (`POST /parking-sessions/entry`, D-038):** accepts **exactly one** of `{ reservationCode }` (≤64) or `{ verificationToken }` (≤4096) via zod `.strict()` + refine (both → `400 VALIDATION_ERROR`). Token path resolves `sub` → digest row, in-tx backfills, verifies byte-for-byte, and enforces the reservation window (`409 TOKEN_NOT_YET_VALID` before `starts_at`, `409 TOKEN_EXPIRED` after `ends_at`), slot `reservationsEnabled` (`409 SLOT_NOT_ENTRYABLE`), `OUT_OF_SERVICE` (`409 SLOT_UNAVAILABLE`), facility state (deactivated/rejected/pending → `409 FACILITY_NOT_ENTRYABLE`), double entry (`409 SESSION_ALREADY_ACTIVE`) and double occupancy (`409 SLOT_OCCUPIED`) via the partial unique indexes; token `sub` must match `^BKG-[0-9A-F]{12}$` (digest-format guard → `409 INVALID_TOKEN`, no bare `randomUUID`/db-id formats). Same-slot concurrency is serialized by the guarded slot-UPDATE + row lock → exactly one `201`.
- **Backend — occupancy integrity (`slots` module):** slot UPDATE preserves operator-set statuses but throws `409 SLOT_IN_USE` when changing **away from** `OCCUPIED` while `hasActiveSessionForSlot` is true, serialized by `SELECT … FOR UPDATE` (race-free vs concurrent entry — whichever side wins the row lock, the other observes the committed outcome); genuine stuck-slot correction (no active session) still works.
